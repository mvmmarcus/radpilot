# 0004: PHI policy (synthetic data, no PHI in logs, and the path to a real deployment)

## Context

RadPilot's domain is clinical radiology reporting, which in a real deployment involves
Protected Health Information (PHI) under HIPAA (US) and personal/sensitive health data
under the LGPD (Brazil, `Lei Geral de Proteção de Dados`, with health data as a
"sensitive personal data" category under Art. 11). This is a demo/portfolio project,
not a regulated deployment, but the codebase is written as if it might become one, so
the policy needs to be explicit about what is true today and what would have to change
for production use with real patients.

## Decision

**Today (this project): synthetic data only, and no PHI in logs, by construction.**

- All patient, study and report data is synthetic, generated by `supabase/seed.sql` and
  `scripts/generate-phantom-dicom.ts` (fixed demo UUIDs, invented names, phantom pixel
  data) — there is no path in this codebase that ingests or stores real patient data at
  all. The README and the FHIR/PDF export headers both carry an explicit "Synthetic
  data, not for clinical use" notice (also an app-shell badge, Track A), because a
  realistic-looking demo is exactly the kind of artifact that gets mistaken for
  something it isn't.
- `src/lib/logger.ts` is a structured logger with an explicit policy in its own
  docstring: "never log patient names, MRNs, report text or prompts. Log ids
  (study_id, report_id, generation_id) instead." This is enforced by convention at
  every call site (there is no field-level scrubber), which is acceptable here because
  the data is synthetic — in a production system this would need to be enforced
  structurally (below).
- `audit_events.payload` is documented as "ids and status changes only. No report text
  or patient identifiers" (`src/modules/audit/domain/event.ts:30`) — the audit trail
  itself is designed to be safe to export or inspect without becoming a second PHI
  store.
- `ai_generations.input`/`output` (jsonb) **do** contain report text (shorthand,
  generated sections) because the acceptance-rate metric and evals need to inspect what
  was generated — this is the one place richer content is persisted, and it is
  access-controlled the same as `reports` (RLS, `authenticated` only), not exempted from
  it.

## Consequences

- Nothing in this repository requires a BAA, DPA, consent flow, or de-identification
  pipeline today, because nothing in it is real patient data. This materially
  simplifies the build (no encryption-at-rest key management beyond what Supabase
  provides, no data residency decision, no breach-notification process to design).
- The explicit "no PHI in logs" rule is cheap to follow now (there is no PHI) but
  documents the invariant the team would need to keep true the moment real data enters
  the system — it's written down so it doesn't have to be rediscovered under pressure
  during a real onboarding.
- `ai_generations` holding full input/output means a production deployment must treat
  that table with the same sensitivity as `reports`, not assume "it's just logs."

## What a production version would need (HIPAA and LGPD)

This section is the honest gap list between this demo and a deployable clinical
product — not implemented here, but worth being explicit about:

- **BAA (Business Associate Agreement) with the LLM vendor, and a DPA (Data Processing
  Agreement) for LGPD.** Sending report shorthand or generated findings to OpenAI or
  Anthropic (`docs/adr/0002-llm-provider-port.md`) means PHI leaves RadPilot's
  infrastructure boundary. HIPAA requires a signed BAA with any vendor that touches PHI
  on the covered entity's behalf; LGPD requires a DPA-equivalent contractual basis
  (Art. 7/11) plus a documented legal basis for processing sensitive health data. Both
  OpenAI and Anthropic offer BAA-eligible enterprise tiers; the provider port
  (`LLMProvider`) would need an adapter configuration that only allows BAA-covered
  endpoints/models in a production environment, and a startup check that refuses to
  boot with `AI_PROVIDER=openai|anthropic` unless that's confirmed.
- **Zero data retention (ZDR) with the model vendor.** Even with a BAA, default vendor
  log retention for abuse monitoring is a real exposure; production use needs a
  contractual zero-retention or short-retention agreement for the specific endpoints
  used, and verification that prompt caching (if used — see the Claude API caching
  reference) doesn't silently extend retention beyond the agreed window.
- **De-identification before any non-essential processing.** Even with a BAA, minimum-
  necessary-use principles argue for stripping patient name/MRN/DOB from the payload
  sent to the LLM wherever the clinical content doesn't require them (shorthand
  findings generation needs modality/body-part/age/sex context, not the patient's
  name or MRN) — a de-identification step belongs in the prompt-building layer
  (`src/modules/ai/application/prompts/`), not bolted on after the fact.
- **Audit coverage for access, not just mutation.** The current `audit_events` table
  captures report lifecycle mutations and exports, which is a strong start, but HIPAA's
  audit-control requirement (45 CFR §164.312(b)) also expects visibility into *read*
  access to PHI (who viewed which patient's study and when) — a production system would
  need read-path auditing, likely sampled or summarized rather than per-request, to
  avoid the audit log itself becoming the dominant write load.
- **Access control beyond "any authenticated user reads everything."** The current RLS
  model (`supabase/migrations/20261001000100_rls.sql`) is explicitly documented as an
  "MVP model: one radiology group... every signed-in user with a profile can read
  clinical data." Multi-tenant or multi-facility production use needs row-level
  facility/department scoping, role-based read restrictions (e.g. a biller shouldn't
  read full report text), and almost certainly minimum-necessary access review per LGPD
  Art. 46 and HIPAA's minimum-necessary standard.
- **Encryption, key management and backup/retention policy** beyond what a managed
  Postgres provider gives by default — explicit key rotation ownership, backup
  encryption, and a defined retention/deletion policy for the audit log and
  `report_versions` history (LGPD's data minimization principle, Art. 6, cuts against
  "keep every version forever" without a stated retention policy).
- **Breach notification and incident response process** — both HIPAA (60-day
  notification to HHS/affected individuals) and LGPD (ANPD notification "in reasonable
  time") require a defined process this demo has no need for today but a production
  fork would need from day one.
- **DICOM/image data handling.** Real pixel data plus embedded DICOM tags (patient name,
  MRN, birth date are standard DICOM header fields) is PHI in a way a JSON report is
  not; a production viewer would need tag scrubbing/de-identification on ingest if images
  ever leave the originating PACS, which this demo's synthetic phantom generator makes
  moot (there is no real DICOM ingest path at all).

## Alternatives considered

- **Use realistic-looking but fabricated PHI (real-sounding names, plausible MRNs) to
  make the demo feel more authentic.** Rejected: increases the risk of the demo being
  mistaken for real data downstream (screenshots, shared seeds) for a purely cosmetic
  gain; synthetic, clearly-fake data plus an explicit UI/export banner is safer and
  costs nothing in demo quality.
- **A field-level PHI scrubber/middleware on the logger today**, even though there's no
  real PHI yet. Considered, but would add complexity to maintain against synthetic data
  that doesn't need scrubbing, with no way to validate it actually works against the
  real shapes production would see. Rejected for now in favor of documenting the
  invariant and the gap list above; a scrubber is the right investment at the point
  real data is first considered, not before.
